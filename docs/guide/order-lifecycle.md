# One Order's Complete Journey

## A code-in-English guide to the matching engine

> **Use this document when you feel lost in the project.**
>
> The final report answers: *what did we measure and what did we learn?*
> `how-it-works.md` answers: *what are the design decisions?*
> This document answers a more concrete question:
>
> **Starting with one order generated by the client, which component touches it,
> what does that component do, where does the order go next, and how can the
> order finally be rejected, cancelled, partially filled, fully filled, or
> rest in the book?**

The explanation follows the actual C++ implementation. File names are included
so that every concept can be connected to source code.

---

## 0. The whole lifecycle in one picture

There are two processes but three important threads:

```text
client process                         matching_engine process
----------------                       --------------------------------------
load_client                            network thread             engine thread
     |                                      |                         |
     | 40-byte TCP message                  |                         |
     +------------------------------------->|                         |
                                            | socket readiness or      |
                                            | I/O completion            |
                                            |                         |
                                            | parse wire message       |
                                            | create Order              |
                                            | stamp enqueue_time        |
                                            |                         |
                                            | push(Order)               |
                                            +-----------> queue --------+
                                                                         |
                                                                         | pop()
                                                                         | shutdown sentinel?
                                                                         | no
                                                                         v
                                                                 MatchingEngine
                                                                         |
                                                   +---------------------+------------------+
                                                   |                                        |
                                             reject before book                       match loop
                                                                                          |
                                                              +---------------------------+------------------+
                                                              |                              |              |
                                                        trade against rest             remainder rests   no match
                                                              |                              |              |
                                                        reduce/cancel rest           book.add(incoming) |
                                                                                          |              |
                                                              +---------------------------+--------------+
                                                                                          |
                                                                                  sink/events/stats
```

The central ownership rule is:

> **Only the engine thread mutates the order book.**

The client never touches the book. The network thread never touches the book.
The queue only transports an `Order`; it does not interpret it. The matching
engine decides what the order means.

## 1. Prerequisites: the vocabulary you need first

### 1.1 What is an order?

The project models a limit order:

```text
Buy  10 units at price 101
Sell  4 units at price 100
```

The fields are defined in `include/order.hpp`:

| Field | Meaning |
|---|---|
| `id` | unique identifier for this order |
| `side` | `Buy` or `Sell` |
| `price` | maximum acceptable price for a buy; minimum acceptable price for a sell |
| `quantity` | how many units remain to trade |
| `submit_time` | when the client sent the order |
| `enqueue_time` | when the network thread parsed it and was about to enqueue it |

`Price` is a signed 64-bit integer and `Quantity` is an unsigned 64-bit integer.
There are no floating-point prices in this project. That avoids rounding
ambiguity in the matching rules.

### 1.2 What is an order book?

The book stores **resting** orders: orders that could not be completely matched
yet.

```text
BUY SIDE                         SELL SIDE
better buy first                 better sell first

price 102: oldest -> newest      price 103: oldest -> newest
price 101: oldest -> newest      price 104: oldest -> newest
price 100: oldest -> newest      price 105: oldest -> newest
```

For bids, the highest price is best. For asks, the lowest price is best. Within
one price level, the oldest order is best. This is **price-time priority**:

1. choose the best price;
2. if several orders have that price, choose the earliest one;
3. only then inspect the next price or the next order.

### 1.3 What does “cross” mean?

An incoming buy crosses the book when:

```text
best ask <= incoming buy price
```

An incoming sell crosses the book when:

```text
best bid >= incoming sell price
```

If the condition is false, the incoming order cannot trade immediately and its
remaining quantity may rest in the book.

### 1.4 What is a trade?

A trade is the result of one incoming order consuming quantity from one resting
order. It contains:

```text
trade id
buy order id
sell order id
execution price
executed quantity
execution timestamp
```

The execution price is the **resting order's price**, not necessarily the
incoming order's price.

Example:

```text
Resting sell: 10 units at 100
Incoming buy:  4 units at 105

Trade: 4 units at 100
```

The buy was willing to pay up to 105, but it receives the resting sell's price
of 100.

## 2. Component map: who owns what?

| Component | Thread | Receives | Does | Must not do |
|---|---|---|---|---|
| `load_client` | client process/thread | workload seed and rate | constructs wire messages and sends bytes | modify the server book |
| TCP socket | kernel | bytes from client | buffers and delivers a byte stream | preserve message boundaries |
| `epoll` or `io_uring` backend | network thread | socket events/completions | obtains received bytes | match orders |
| wire parser | network thread | arbitrary byte chunks | reconstructs 40-byte messages and rejects malformed messages | decide book behaviour |
| `Order` | initially network, then engine | parsed fields | carries state across the boundary | be modified by network after enqueue |
| mutex ring buffer | network + engine | `Order` | transfers with a mutex and condition variables | inspect prices or quantities |
| SPSC ring buffer | network + engine | `Order` | transfers with atomic indices and release/acquire ordering | support multiple producers |
| `MatchingEngine<Book, Sink>` | engine thread | one `Order` at a time | validates, matches, rests, emits results | perform network I/O |
| V1 `OrderBook` | engine thread | book operations | stores orders in maps/lists | decide whether an incoming order crosses |
| V3 `OrderBookFast` | engine thread | same book interface | stores orders in arrays/intrusive lists/bitmap/hash | decide matching policy |
| slab or heap allocator | engine thread | node allocation request | returns storage for resting nodes | own network or queue state |
| `CountingSink` / event sink | engine thread | trades/events | counts, logs, or forwards results | change the book |

The separation is intentional. The book answers questions such as “what is the
oldest order at the best ask?” The matching engine asks those questions and
decides what to do.

## 3. Stage A — the client creates an order

The client is `tools/load_client.cpp`. Conceptually, one iteration does this:

```text
order_id  = next id
side      = Buy or Sell
price     = workload price
quantity  = workload quantity
timestamp = CLOCK_MONOTONIC now

message = encode_little_endian(order_id, side, price, quantity, timestamp)
send(message)
```

The wire message is exactly 40 bytes, defined in `include/wire.hpp`:

```text
offset  size   field
0       8      id
8       1      side: 0 = Buy, 1 = Sell
9       7      padding
16      8      price
24      8      quantity
32      8      client timestamp in monotonic nanoseconds
```

### Why is the timestamp written before `send()`?

Because the project wants to measure the complete path:

```text
client timestamp
      |
      | client work + send + TCP loopback + network scheduling
      v
network parse / enqueue_time
      |
      | queue wait + matching + book update
      v
engine completion timestamp
```

If the timestamp were written after the send, the measured latency would omit
part of the order's journey.

### Important TCP fact: `send()` does not equal “one message received”

TCP is a byte stream, not a message queue. The server may receive:

```text
one message in one recv()
half a message in one recv()
three messages in one recv()
half of one message followed by one complete message
```

Therefore the network backend keeps a 4096-byte connection buffer and the wire
parser carries incomplete trailing bytes into the next read.

## 4. Stage B — the kernel and TCP deliver bytes

The client and server communicate over TCP, normally through loopback on the
same host. The kernel manages:

1. the client socket;
2. the server listening socket;
3. the established connection;
4. receive buffers;
5. readiness or completion notifications.

The server enables `TCP_NODELAY`, which avoids deliberately waiting to combine
small writes using Nagle's algorithm. This does **not** make TCP message-based;
the parser is still required.

There are two interchangeable ways for the network thread to learn that bytes
are available.

### Option N1 — `epoll`: readiness-based I/O

`src/network_epoll.cpp` follows this loop:

```text
create listening socket
bind and listen
make listener non-blocking
register listener with epoll

repeat:
    epoll_wait(...)
    for every ready descriptor:
        if it is the listener:
            accept all currently waiting connections
        else:
            repeatedly recv() until:
                EAGAIN/EWOULDBLOCK, or
                disconnect, or
                fatal error
            parse every complete 40-byte message
```

**Readiness** means: “the file descriptor probably will not block if you try
to perform this operation.” `epoll` does not itself receive the order; the
subsequent `recv()` does.

The connection uses edge-triggered mode (`EPOLLET`), so the backend must drain
the socket until `EAGAIN`. Stopping after one `recv()` could leave unread data
without another edge notification.

### Option N2 — `io_uring`: completion-based I/O

`src/network_io_uring.cpp` follows a different shape:

```text
create an io_uring submission/completion queue
submit one accept request

repeat:
    wait for a completion queue entry (CQE)
    if it is an accept completion:
        register the new connection
        submit one recv request for it
    if it is a recv completion:
        append received bytes to the connection buffer
        parse complete messages
        submit the next recv request
```

**Completion-based** means: “the kernel has finished the operation and reports
the result.” The project deliberately uses one-shot accept and receive
operations. It does not use multishot receive or `SQPOLL`, because those would
change the mechanism being compared.

### What is the same between the two backends?

Both backends:

- use the same 40-byte wire format;
- use a 4096-byte partial-message buffer per connection;
- call the same `wire::parse()` function;
- convert the same wire message into the same `Order`;
- stamp `enqueue_time` at the same logical point;
- call the same queue `push()` function.

Only the way bytes are obtained differs.

## 5. Stage C — parsing converts bytes into an `Order`

`wire::parse()` in `include/wire.hpp` is a small state machine over the connection
buffer.

```text
while buffer contains at least 40 bytes:
    copy the next 40 bytes into wire::Msg
    advance offset by 40

    if id == 0, side > 1, or quantity == 0:
        invalid++
        discard this message
    else:
        call the message callback

move any incomplete trailing bytes to buffer[0...]
return number of trailing bytes
```

The parser does not reject a duplicate order ID or an out-of-range V3 price.
Those checks require book state and therefore happen later inside the matching
engine.

For a valid message, `wire::toOrder()` maps:

```text
wire id          -> Order.id
wire side 0      -> Side::Buy
wire side 1      -> Side::Sell
wire price       -> Order.price
wire quantity    -> Order.quantity
wire timestamp   -> Order.submit_time
```

Then the network thread obtains `steady_clock::now()` and writes:

```text
Order.enqueue_time = now
```

Finally it calls the queue's `push(o)`.

### The first rejection branch

Malformed wire messages end here:

```text
bytes -> parse -> invalid message -> increment invalid counter -> discard
```

They never become an `Order`, never enter the queue, never reach the book, and
do not produce a matching-engine `OrderRejected` event. That distinction matters:

| Rejection location | Example | Counted by |
|---|---|---|
| wire parser | `id == 0`, invalid side, zero quantity | network `invalid` counter |
| matching engine | duplicate ID, unsupported V3 price, book capacity failure | engine rejected counter/events |

## 6. Stage D — the order crosses the thread boundary

At this point the network thread has finished writing the `Order`. It passes a
`const Order&` to `push()`, which copies the order into the queue slot. After
that call returns, the network thread does not modify that queued copy.

There are two queue implementations.

### Queue Q1 — mutex ring buffer

Implemented by `RingBuffer` and `src/ring_buffer.cpp`.

```text
push(order):
    lock mutex
    if count == capacity:
        full_waits++
        sleep on not_full until space exists
    buffer[tail] = order
    tail = (tail + 1) modulo capacity
    count++
    unlock mutex
    notify one consumer on not_empty

pop():
    lock mutex
    if count == 0:
        empty_waits++
        sleep on not_empty until an order exists
    order = buffer[head]
    head = (head + 1) modulo capacity
    count--
    unlock mutex
    notify one producer on not_full
    return order
```

The condition variable is a kernel-assisted sleep/wake mechanism. It saves CPU
when idle, but waking the other thread introduces scheduling work and potential
run-queue delay.

### Queue Q2 — lock-free SPSC ring buffer

Implemented by `SpscRingBuffer` in `include/spsc_ring_buffer.hpp`.

SPSC means **single producer, single consumer**. Here:

```text
producer = network thread
consumer = engine thread
```

The producer alone writes `tail_`. The consumer alone writes `head_`. Both may
read the other side's index.

```text
try_push(order):
    read producer-owned tail
    if queue looks full:
        refresh cached head with acquire load
        if genuinely full: return false
    write order into buf[tail & mask]
    publish tail with release store
    return true

push(order):
    if try_push succeeds: return
    full_waits++
    repeatedly try_push:
        first 4096 attempts: CPU pause hint
        after that: periodically std::this_thread::yield()

try_pop():
    read consumer-owned head
    if queue looks empty:
        refresh cached tail with acquire load
        if genuinely empty: return false
    copy buf[head & mask] into local Order
    publish head with release store
    return true

pop():
    if try_pop succeeds: return order
    empty_waits++
    repeatedly try_pop using the same pause/yield policy
```

### Why release/acquire is needed

The producer must not publish “slot ready” before it has written the `Order`.
The consumer must not read the slot before it observes that publication.

```text
producer: write Order -> tail.store(release)
consumer: tail.load(acquire) -> read Order
```

On the return path:

```text
consumer: read Order -> head.store(release)
producer: head.load(acquire) -> reuse slot
```

`release` publishes prior writes. `acquire` makes those writes visible to the
other thread. The queue is lock-free in its data-transfer algorithm, but its
blocking `push()`/`pop()` functions may spin and occasionally yield while
waiting.

### What the queue does not do

The queue does not:

- validate price-time rules;
- detect duplicate IDs;
- match orders;
- allocate book nodes;
- produce trades;
- know whether an order will rest or fill.

It only preserves the order object while handing it from one thread to another.

## 7. Stage E — the engine receives one order

The engine thread calls `queue->pop()` and receives a local `Order o`.

The main loop in `src/main.cpp` then performs this high-level sequence:

```text
o = queue.pop()
if o.id == 0:
    stop: this is the reserved shutdown sentinel

t0 = o.submit_time
engine.process(o)
t1 = steady_clock.now()

record t1 - t0 as total latency
record o.enqueue_time - t0 as arrival latency
record t1 - o.enqueue_time as service latency
```

`MatchingEngine::process()` copies the incoming order into a local variable:

```cpp
Order in = incoming;
```

This local `in.quantity` is allowed to shrink as it consumes resting orders.
The original order object in the queue is no longer needed.

The engine reads one clock timestamp, `now`, for the processing call. All events
and trades caused by that order share this timestamp. That avoids a clock read
for every tiny event.

## 8. Stage F — early validation and rejection branches

Before inspecting the book, the engine evaluates:

```cpp
if (in.quantity == 0 ||
    !book.validPrice(in.price) ||
    book.contains(in.id)) {
    emit(OrderRejected)
    return;
}
```

This is the first engine-level decision tree:

```text
                         incoming Order
                              |
       +----------------------+----------------------+
       |                      |                      |
 quantity == 0          invalid price           duplicate id
       |                      |                      |
       +----------------------+----------------------+
                              |
                    OrderRejected, no book change

                              or

                 all three checks pass
                              |
                    OrderAccepted event
                              |
                         match it
```

### Difference between V1 and V3 here

The same engine calls `book.validPrice()` through the book interface, but the
answers differ:

| Book | `validPrice(price)` |
|---|---|
| V1 `OrderBook` | always true; it uses `std::map` and accepts any price |
| V3 `OrderBookFast` | true only when `min_price <= price < min_price + NumLevels` |

Therefore the same incoming order may pass V1 validation but be rejected by V3
because its price cannot be represented in V3's fixed array.

If validation succeeds, the engine emits `OrderAccepted` **before** matching.
This does not mean the order will necessarily rest. It means the order passed
the initial engine checks.

## 9. Stage G — the matching decision tree

The engine saves:

```text
original_quantity = in.quantity
```

Then it chooses a side-specific loop.

### Incoming buy

```text
while incoming quantity > 0
  AND the book has at least one ask
  AND best ask price <= incoming buy price:

    resting = oldest order at the best ask
    fill(incoming, resting)
```

### Incoming sell

```text
while incoming quantity > 0
  AND the book has at least one bid
  AND best bid price >= incoming sell price:

    resting = oldest order at the best bid
    fill(incoming, resting)
```

The two loops are mirror images. The only difference is which opposite side is
examined and which price comparison defines a cross.

### Why does the loop repeat?

One incoming order can consume several resting orders:

```text
resting asks:
    ask 100: A quantity 3
    ask 100: B quantity 4
    ask 101: C quantity 5

incoming buy: quantity 10, limit price 101
```

The incoming buy may execute in this exact order:

```text
1. A: 3 at 100; incoming remainder = 7
2. B: 4 at 100; incoming remainder = 3
3. C: 3 at 101; incoming remainder = 0
```

The engine never skips B to reach C. Time priority applies within price 100.

## 10. Stage H — one fill in detail

`MatchingEngine::fill()` handles one incoming/resting pair.

Suppose:

```text
incoming quantity = 7
resting quantity  = 4
```

The fill quantity is:

```text
q = min(7, 4) = 4
```

The implementation then performs these operations in order:

```text
1. allocate the next TradeId
2. choose buy_order_id and sell_order_id from the two orders
3. use resting.price as execution price
4. set trade quantity = q
5. send Trade to sink
6. emit TradeExecuted event
7. reduce incoming.quantity by q
8. reduce resting order by q in the book
9. emit a full-fill or partial-fill event for the resting order
```

The engine copies the resting ID, price and quantity **before** calling
`reduce()`, because a full reduction may destroy the resting node.

### Fill outcome matrix

| Incoming quantity | Resting quantity | `q` | Incoming after fill | Resting after fill | Resting event |
|---:|---:|---:|---:|---:|---|
| 7 | 4 | 4 | 3 | removed | `OrderFullyFilled` |
| 4 | 7 | 4 | 0 | 3 remains | `OrderPartiallyFilled` |
| 4 | 4 | 4 | 0 | removed | `OrderFullyFilled` |

The event is named from the **resting order's** point of view inside `fill()`.
After the loop, the engine separately emits the appropriate terminal event for
the incoming order.

## 11. Stage I — what happens to the resting order?

The book exposes two operations for this:

```text
book.reduce(resting_id, q)
book.cancel(resting_id)
```

### Partial reduction

If `q < resting.quantity`:

```text
resting.quantity -= q
resting remains at the same position in its price-level FIFO list
```

This is important: a partially filled order does **not** lose time priority.

### Full reduction

If `q == resting.quantity`:

```text
unlink resting node from its level
remove resting id from the ID index
if the price level is now empty:
    remove/clear the price level
    update the best-price metadata
release the node's storage in V3
```

The next order at the same price becomes the new front. If that was the last
order at the price, the engine searches for the next best non-empty price.

### Explicit cancellation

The engine's matching path calls `reduce()` for fills. The book also provides
`cancel(id)` for an explicit cancellation operation or a test. Cancellation:

```text
find id in the ID index
if absent: return false
unlink it from its FIFO level
remove its ID-index entry
update empty-level/best-price metadata if needed
release node storage when using V3
return true
```

Cancellation removes the complete remaining quantity. It produces no trade.

This project's network wire format generates normal orders, not a separate
cancel message. The cancellation API exists as book functionality and is tested,
but the benchmark workload's normal lifecycle ends through matching, resting,
rejection, or shutdown.

## 12. Stage J — the incoming order's terminal branches

When the matching loop stops, there are three possibilities.

### Outcome 1 — fully filled

```text
in.quantity == 0
```

The incoming order has consumed all of its requested quantity. The engine emits:

```text
OrderFullyFilled(incoming id, original quantity)
```

The incoming order is not inserted into the book.

### Outcome 2 — partially filled, then remainder rests

```text
0 < in.quantity < original_quantity
```

The engine first emits:

```text
OrderPartiallyFilled(incoming id, filled quantity)
```

Then it tries to insert the remaining `in` into the book:

```text
book.add(in)
```

If insertion succeeds, the order's remainder becomes the newest order at its
price level.

### Outcome 3 — no fill, then the whole order rests

```text
in.quantity == original_quantity
```

The order did not cross any opposite-side liquidity. The engine still calls:

```text
book.add(in)
```

If insertion succeeds, the entire order becomes a new resting order at the back
of its price-level queue.

### The final `book.add()` can fail

The engine treats failure to store a remainder as a rejection:

```text
if (!book.add(in)) {
    emit(OrderRejected)
    rejected_remainders++
}
```

This can happen in V3 when:

- the price is outside its fixed range;
- the slab/pool has no free node;
- the ID is already present, although the early duplicate check normally prevents
  this path.

In V1, price range and pool exhaustion do not occur because `std::map` and
`std::list` grow dynamically, but duplicate IDs and zero quantity are still
rejected.

This is the lifecycle in algorithm form:

```text
receive bytes
    |
    +-- incomplete 40-byte message --> keep bytes for next read
    |

    |
    +-- valid message --> construct Order; stamp enqueue_time; queue.push
                              |

                              |                                             |
                              | mutex: sleep until space                   |

                              |                                             |

                                                                            |
```

## 14. The two book implementations: same lifecycle, different machinery

The engine is templated as `MatchingEngine<Book, Sink>`. It calls the same
logical methods in either implementation:

```text
validPrice
contains
hasBid / hasAsk
bestBid / bestAsk
frontAtBestBid / frontAtBestAsk
add
reduce
cancel
```

The matching algorithm does not know which book it received.

### B1 — V1 reference book: `std::map` + `std::list`

Data structure:

```text
bids_: std::map<Price, std::list<Order>, std::greater<Price>>
asks_: std::map<Price, std::list<Order>>
index_: std::unordered_map<OrderId, Locator>
```

For a buy:

```text
bids_.begin() = highest bid
asks_.begin() = lowest ask
level.front() = oldest order at that price
level.push_back(order) = newest order at that price
```

An `unordered_map` locator lets `cancel(id)` or `reduce(id, q)` find the list
iterator without scanning the entire book.

**Advantages:** simple, general price range, useful correctness baseline.

**Costs:** tree nodes, list nodes, pointer chasing, dynamic allocation, possible
hash-table growth/rehashing, and less predictable tails.

### B2 — V3 optimized book: array + intrusive list + bitmap + flat hash

Data structure:

```text
price p -> levels_[p - min_price]
each level -> head Node* and tail Node*
Node -> Order + prev pointer + next pointer
id -> Node* through a pre-sized open-addressing hash table
non-empty prices -> two-level bitmap
```

An **intrusive list** means the `prev` and `next` pointers live inside the order
node itself. The book does not allocate a separate list object per link.

When adding the first order at a price, V3:

```text
set the corresponding bitmap bit
increment the number of non-empty levels
update best_bid_ or best_ask_
```

When removing the last order at a price, V3 clears the bit and finds the next
best set bit using `ctz`/`clz` (count trailing/leading zero bits).

**Advantages:** direct price indexing, fixed-size nodes, no per-order heap call
with the slab, no hash rehash, fast best-price discovery, predictable capacity.

**Costs:** fixed price window, fixed maximum resting orders, reserved memory, and
more metadata-maintenance code.

## 15. Allocation choices: slab versus heap

V3's `Node` is 64-byte aligned and exactly one cache line:

```text
Node = Order + prev pointer + next pointer = 64 bytes
```

### A1 — slab allocator (`fast-slab`)

At startup:

```text
allocate one large block
divide it into fixed-size Node slots
write a next-free pointer inside every free slot
free_head points to the first slot
```

On `add()`:

```text
if free_head == nullptr:
    fail: capacity exhausted
slot = free_head
free_head = slot's next-free pointer
placement-new Node in slot
```

On full removal:

```text
destroy Node
write current free_head into its storage
free_head = this slot
```

The free list is **in-place**: it uses the memory of free objects rather than a
separate bookkeeping array. Allocation and deallocation are O(1), with no heap
call on the matching hot path.

### A2 — aligned heap allocator (`fast-heap`)

The same V3 data structures are retained. The only intended difference is node
storage:

```text
allocate -> aligned operator new
remove   -> aligned operator delete
```

This is the control experiment: it asks whether the slab itself explains a
measured difference, without also changing the book algorithm.

### Important distinction

`fast-heap` is not V1. V1 changes the data structures too. The useful comparisons
are:

| Comparison | What it isolates |
|---|---|
| V1 vs V3 slab | data structure + allocation strategy together |
| V3 slab vs V3 heap | allocator choice while book structure stays fixed |
| V1 vs V3 heap | data structure improvement without slab advantage |

## 16. The complete configuration matrix

The executable dispatches these choices in `src/main.cpp`.

### 16.1 Independent component choices

| Dimension | Options | What changes for an order |
|---|---|---|
| queue | `mutex`, `spsc` | how the `Order` waits between network and engine threads |
| book | `v1`, `fast-slab`, `fast-heap` | how resting orders are indexed, linked, found, and removed |
| network | `epoll`, `uring` | how received socket bytes wake/complete the network thread |
| scheduling | `default`, `pin`, `rt` | where/how the engine thread is scheduled |
| network affinity | floating or `--cpu-net N` | whether the network thread may migrate |
| client affinity | normally CPU 6 in experiments | where the generator runs |

The primary Cartesian product is:

```text
2 queue choices
× 3 book choices
× 2 network choices
× 3 scheduling choices
```

That is 36 theoretical command-line combinations, although not every one is a
headline experiment and `rt` requires permission that the measured host denied.
The paper's main latency matrix holds the book fixed and compares:

```text
2 queues × 2 scheduling modes × 2 network backends
= 8 integrated configurations
```

Other experiments deliberately change only the dimension being studied:

| Experiment | Fixed | Varied |
|---|---|---|
| queue comparison | book, network, scheduling | mutex vs SPSC |
| network comparison | book, queue, scheduling | epoll vs io_uring |
| affinity comparison | book, queue, network | default vs engine pinned |
| allocator comparison | book algorithm, queue, network | V3 slab vs V3 heap |
| book comparison | queue, network, scheduling | V1 vs V3 |
| saturation | selected queue/book/network | offered client rate |

### 16.2 What a single option can and cannot change

```text
--queue changes the hand-off mechanism only.
--book changes storage and lookup inside the engine only.
--net changes byte acquisition only.
--sched changes engine scheduling policy/affinity only.
--cpu-net optionally changes network-thread affinity.
```

The order's semantic rules do not change between these options. If a valid order
matches in one configuration, the checksum tests expect the same trades,
quantity, and notional in the others.

## 17. Concrete worked lifecycles

These examples show the branches without hiding behind abstractions.

### Example A — buy crosses one sell and rests a remainder

Initial book:

```text
ask 100: order S1, quantity 4
ask 101: order S2, quantity 5
```

Incoming wire message:

```text
id= B1, side=Buy, price=101, quantity=7
```

Lifecycle:

```text
1. client encodes B1 and sends 40 bytes
2. network backend receives bytes
3. parser validates id/side/quantity
4. network creates Order B1 and stamps enqueue_time
5. queue transfers B1 to engine
6. engine validates B1; it is accepted
7. best ask is 100; 100 <= 101, so B1 crosses S1
8. trade T1: buy B1, sell S1, quantity 4, price 100
9. S1 is fully reduced and removed
10. B1 remainder is 3
11. best ask is now 101; 101 <= 101, so B1 crosses S2
12. trade T2: buy B1, sell S2, quantity 3, price 101
13. B1 remainder is 0
14. S2 remains with quantity 2
15. B1 receives OrderFullyFilled
16. B1 is not inserted into the book
```

Final book:

```text
ask 101: order S2, quantity 2
```

### Example B — buy does not cross and rests

Initial book:

```text
ask 105: S1 quantity 4
```

Incoming:

```text
B1 Buy price=103 quantity=7
```

Decision:

```text
best ask = 105
105 <= 103 is false
```

No trade is created. `book.add(B1)` appends B1 to bid price 103. The incoming
order is accepted and resting, not rejected.

### Example C — partial fill, then remainder rests

Initial book:

```text
ask 100: S1 quantity 4
ask 102: S2 quantity 10
```

Incoming:

```text
B1 Buy price=101 quantity=7
```

Only S1 crosses:

```text
trade 4 at 100
B1 remainder = 3
best ask = 102; 102 <= 101 is false
book.add(B1 with quantity 3)
```

The B1 remainder joins the back of bid price 101.

### Example D — invalid before the book

```text
wire quantity = 0
```

The wire parser discards this message before an `Order` reaches the queue.

Alternatively:

```text
wire quantity = 4
V3 price outside [min_price, min_price + NumLevels)
```

The parser accepts the message because the wire shape is valid. The engine later
calls V3 `validPrice()`, emits `OrderRejected`, and leaves the book unchanged.

### Example E — duplicate ID

Suppose `B1` is already resting. A second incoming order with `id=B1` arrives.

```text
parser: valid wire message
queue: transfers it normally
engine: book.contains(B1) == true
engine: emits OrderRejected
engine: does not match or add it
```

The ID index is what makes this check fast.

### Example F — V3 capacity exhaustion

If all `MaxOrders` V3 nodes are occupied and an unmatched remainder must rest:

```text
matching may have produced trades already
book.add(remainder) -> slab.allocate() returns nullptr
engine emits OrderRejected for the remainder
```

This is a subtle case: an order can be accepted initially, partially filled,
and then have its unfilled remainder rejected because there is no storage.

## 18. Every terminal state, in one table

| Terminal state | Did it enter queue? | Did engine run? | Did it trade? | Did it enter book? |
|---|---:|---:|---:|---:|
| malformed wire message | no | no | no | no |
| engine rejects zero quantity | yes, unless wire parser caught it | yes | no | no |
| engine rejects invalid V3 price | yes | yes | no | no |
| engine rejects duplicate ID | yes | yes | no | no |
| fully filled incoming order | yes | yes | yes, one or more | no |
| partially filled and remainder rests | yes | yes | yes | yes, remainder |
| no fill and rests | yes | yes | no | yes, full quantity |
| remainder rejected after fills | yes | yes | yes | no remainder |
| explicit cancellation of resting order | not a normal wire path in this benchmark | engine/book API | no new trade | removed |
| shutdown sentinel | queue only | loop exits | no | no |

The word **accepted** is not identical to **rested** and not identical to
**fully filled**. In this implementation, `OrderAccepted` means the early engine
validation passed. The final state is decided only after the matching loop and
the possible `book.add()`.

## 19. What the sink and EventManager see

The matching engine has two output concepts:

```text
Trade       = the economic execution: two order IDs, price, quantity
EngineEvent = lifecycle notification: accepted/rejected/trade/partial/full
```

`CountingSink` receives both and updates counters:

```text
accepted
rejected
trade_events
partial_fills
full_fills
trades
traded_quantity
traded_notional
```

The benchmark uses those values as a correctness checksum. If V1 and V3 produce
different trade count, traded quantity, or notional for the same deterministic
input stream, the performance comparison is invalid.

When `--log` is enabled, `src/main.cpp` builds this path:

```text
MatchingEngine
      |
      v
EventManagerSink -> EventManager -> TradeLogSink listener -> CSV file
```

The normal measured runs use `CountingSink` directly so logging and file I/O do
not pollute latency measurements. `TeeSink` can send the same event to two sinks.

## 20. Shutdown is also part of the lifecycle

An order is not the same thing as the shutdown marker.

When the client disconnects and `--exit-on-disconnect` is enabled:

```text
network server stops accepting/servicing the connection
network thread finishes
network thread creates Order sentinel with id = 0
network thread pushes sentinel into queue
engine pops sentinel
engine sees id == 0
engine exits without calling MatchingEngine::process()
threads join
statistics are written
```

`id == 0` is reserved for this sentinel, which is why the wire validator rejects
zero IDs. A real order must never use ID zero.

## 21. How the benchmark observes the lifecycle

For a measured order, the main loop records three times:

```text
submit_time   = client timestamp
enqueue_time  = network-thread timestamp after parsing
completion    = engine-thread timestamp after process()
```

Then:

```text
arrival latency = enqueue_time - submit_time
service latency = completion - enqueue_time
total latency   = completion - submit_time
```

The total is approximately the two components, but percentiles do not add
exactly because p99.9 arrival and p99.9 service can belong to different orders.

The benchmark also records:

| Measurement | What it tells you |
|---|---|
| p50/p95/p99/p99.9/max | distribution shape and tail |
| `engine_runq_ns` | time engine was runnable but waiting for a CPU |
| `net_runq_ns` | same for network thread |
| voluntary context switches | sleeps/wakes, especially mutex condition-variable behaviour |
| involuntary context switches | preemption |
| queue full waits | producer found no free slot |
| queue empty waits | consumer found no order |
| `spsc_yields` | long SPSC waits that periodically yielded |
| invalid messages | malformed wire inputs |
| trades/quantity/notional | semantic correctness checksum |

This is why the report can say “the tail was ingress” rather than simply saying
“the system was slow”: the timestamp split and run-queue counters identify which
thread waited.

## 23. Final mental model

Do not picture the project as “a fast order book” alone. Picture this:

```text
bytes arrive
    -> bytes are reconstructed into a valid Order
    -> Order waits at a thread boundary
    -> engine validates it against current book state
    -> engine repeatedly consumes best opposite orders
    -> each fill reduces or removes a resting order
    -> incoming remainder either rests or is rejected
    -> trades/events/counters leave the engine
    -> timestamps explain where the time went
```

The central design is deliberately narrow:

```text
network thread owns ingestion
queue owns transfer
engine thread owns matching decisions
book owns resting-order storage
allocator owns node storage
sink owns observation/output
```

Once that ownership chain is clear, the many permutations stop looking like
unrelated features. Every command-line option changes one link in the same
lifecycle:

```text
epoll vs io_uring       changes how bytes reach the parser
mutex vs SPSC           changes how Orders cross into the engine
V1 vs V3                changes how resting Orders are found and stored
slab vs heap            changes how V3 nodes receive memory
default vs pin/rt       changes how the two worker threads receive CPU time
```

The order's meaning and matching rules stay the same. The experiment changes the
cost and predictability of carrying out those rules.
